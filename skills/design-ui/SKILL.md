# Design UI

User-invoked only: follow this skill only when the user ran `/design-ui`. When the work belongs to another skill, name it (for example `/code-fix`), say why, and stop. Do not invoke it yourself.

Prefix your first line with 🥷 inline, not as its own paragraph.

If it could have been generated by a default prompt, it is not good enough.

Done means the real rendered surface was checked against the user's visual goal at every supported viewport and state, or the exact view left unchecked is named.

## Ground rules

- **No em dash.** Never use U+2014 in any output from this skill. Use commas, colons, or periods.
- **Gut-feel complaints are aesthetic.** "很傻", "很怪", "突兀", "不协调", "不和谐" reject the look. They are not a bug report. A deterministic broken render, state, or timing path is `/code-fix`.
- **Current evidence wins.** The screenshot, the rendered output, and the repo's `DESIGN.md` override memory and earlier preferences.
- **UI copy cuts** follow the UI copy rules in [references/design-reference.md](references/design-reference.md), in every mode.
- **Print documents are out of scope.** For a report, deck, resume, or paged PDF, tell the user to run a document typesetting skill (such as `/kami`) when one is installed, and stop. Screen layout (app surfaces, components, web pages) stays here.

## Build a surface

### 1. Read what already exists

The existing product is the first source of direction. Look before choosing anything:

```bash
ls DESIGN.md 2>/dev/null
rg --files . | rg -i '(tokens|theme|colors|variables)\.(css|scss|ts|js|json)$|tailwind\.config'
rg -l '<Dialog|<Sheet|<Toast|<Popover|<Drawer' src     # siblings of what you are about to build
git log --oneline -15 -- <style or component paths>
```

When the app already has a component of the same class (panel, dialog, sheet, toast, confirmation), reuse its container, motion, and type tokens. A new style needs a stated reason why no existing component fits. A first draft that ignores the app's own vocabulary gets rejected on sight. If `DESIGN.md` exists, its tokens beat a fresh palette.

When the user hands over a repository or source to recreate or extend, read the actual theme and token files, global styles, and the named components. Lift exact values: hex codes, spacing steps, font stacks, radii. Never reconstruct from memory. Skip `.git`, `node_modules`, `dist`, and lockfiles.

### 2. Resolve the direction

Answer five questions from evidence, in this order: the current product's tokens and siblings, other shipped products by the same team, then the conversation. Model-default palettes, fonts, and freehand graphics are a last resort. An existing product may answer all five with no question to the user.

1. **Who uses it, and in what context?** An analyst dashboard is not a landing page.
2. **What is the aesthetic direction?** Name it precisely: dense editorial, raw terminal, ink on paper, brutalist grid, warm analog. "Clean and modern" is not a direction. "Feels like Linear" is not a direction either: extract three properties from the reference (button radius, how surfaces separate: shadow, background step, or border; and the accent family) and name those.
3. **What is the signature?** One typeface, color system, motion, or asymmetric layout, made obvious.
4. **What are the hard constraints?** Framework, bundle size, contrast minimums, keyboard access.
5. **What is the signature micro-interaction?** Scale on press, staggered reveal, an animated icon, or deliberately none for a quiet utility.

Infer first. State the strongest inferred answer for each open question. Ask once, at most two sub-questions, and only where the answer would change the deliverable. Silence accepts the stated assumption; a contradicting answer reopens only that question. Do not write code until all five are settled by evidence, a stated assumption, or an answer.

When a well-known brand's exact tokens would settle a direction that is still open, offer the Reference-site Brand Presets in [references/design-reference.md](references/design-reference.md). Run them only with approval.

Survey 2 or 3 mature products only for a genuinely unfamiliar interaction pattern. Record one concrete decision from each. Skip it for cosmetic fixes and established siblings.

**Special surfaces:**

- **Existing native app** (macOS, iOS, Android) with a coherent look: do not propose a wholesale port to a newer platform style (Liquid Glass, Material You, Fluent) unless asked this turn. State the current direction in one sentence, then polish spacing, alignment, states, hierarchy, copy, and timing. For motion or press states, load [references/design-native-motion.md](references/design-native-motion.md).
- **App shell** (sidebar plus workspace, Slack or Linear class): load App Shell Rules in [references/design-reference.md](references/design-reference.md).
- **Dashboard or chart-heavy view**: load [references/design-data-viz.md](references/design-data-viz.md).

### 3. Write the direction down

State the direction in one sentence, then three lines before any code:

- **Visual thesis**: mood, material, and energy. "Warm brutalist editorial, high-contrast ink type, rough paper texture."
- **Content plan**: hero, support, detail, final CTA, one line each. For an app or dashboard: orient, show status, enable action. No hero unless asked.
- **Interaction thesis**: `none` with a reason, or 2 or 3 specific motions that change how the page feels.

For a production or multi-page UI, write or update `DESIGN.md` first ([Write DESIGN.md](#write-designmd)). For one component, the three lines are enough.

### 4. Build

Load [references/design-reference.md](references/design-reference.md). Check its tech stack conflicts table and name one CSS strategy before the first component. Tokens, production craft, accessibility, and motion timing live there.

### 5. Render and check

Check the render, not the source. Early wraps, orphaned separators, and overflow are invisible in code.

```bash
# web: both sides of every breakpoint
npx playwright screenshot --viewport-size=375,812  --full-page <url> "$TMPDIR/ui-375.png"
npx playwright screenshot --viewport-size=1280,800 --full-page <url> "$TMPDIR/ui-1280.png"
```

- Web: phone (375, plus 320 for button rows) and desktop (1280), every shipped locale, long words inside buttons, tabs, and compact cards.
- Native: minimum width, minimum height, both together, and normal size.
- States the change can reach: default, hover and focus, selected, loading, empty, error.
- Alignment and spacing claims close with numbers: the two boxes' `getBoundingClientRect()` before and after, plus the viewport width.

Read every screenshot you take. If the host cannot render, say so and name the exact view the user should check.

### 6. Review and hand off

Re-read the visual thesis. If the screen drifted toward a generic default, find the element that broke first (typeface, color, card treatment, spacing) and fix it.

A new page or visual system also runs the Aesthetic Review Checks in [references/design-reference.md](references/design-reference.md). Every surface runs the AI slop test: would a stranger glancing at the first viewport say an AI made this? Scan for the Absolute Bans and Common Traps (reflex font, default gradient, centered hero with two side-by-side CTAs, three identical cards, generic top nav) and fix any that the direction did not ask for.

End with:

- The aesthetic direction, named and justified in 2 or 3 sentences.
- The non-obvious choices: typeface, color, layout logic.
- How to replace placeholder content with real content.
- The viewports and states checked, and any left unchecked.

Then stop.

## Write DESIGN.md

Use this path when the user asks to create or edit the design system file, or passes a style brief. Do not implement UI in the same pass.

Read [references/specification.md](references/specification.md) before writing. The file is `DESIGN.md` at the git root. There is no second design-system file.

The brief is the user's description of the look. If it is empty, ask for audience, mood, references, and constraints. Do not invent a brand. If `DESIGN.md` exists, keep every token and paragraph the user did not ask to change.

1. YAML front matter first: `version: alpha`, `name`, then tokens (`colors`, `typography`, `rounded`, `spacing`, `components` as needed). Cross-reference with `{path.to.token}`. Omit an unused group through `omitted` with a reason, not an empty stub.
2. Body sections in spec order: Overview, Colors, Typography, Layout, Elevation & Depth, Shapes, Components, Do's and Don'ts. Skip one only when it does not apply.
3. Tokens are normative. Prose explains why and how. Every hex or size in prose matches a token.
4. Prefer hex colors. Then run `npx --yes @google/design.md lint DESIGN.md` when network and tooling allow, and fix what it reports.

## When asked for options

Give at least 3 variations that differ on real dimensions. The Options Guide in [references/design-reference.md](references/design-reference.md) names the dimensions and the basic-to-bold progression.

Offer two labeled candidates unasked when the choice is taste, not correctness (icon, weight, accent, motion feel): the reply becomes one letter instead of a rewrite. For a structural change, describe the end state in a sentence or two and get a nod before writing code.

## Hard rules

Always on, in every mode. Quick-fix and screenshot paths use this compact list instead of loading the full reference. Each ban has its rewrite in the Absolute Bans table of [references/design-reference.md](references/design-reference.md): no thick side-border accents, gradient text, default glass cards, reflex purple-to-blue or cyan-on-dark palettes, generic rounded shadow-card grids, modals for ordinary overflow, `transition: all`, or animated layout properties.

Two motion rules apply everywhere. Frequency decides whether something animates: nothing keyboard-initiated animates, and anything triggered hundreds of times a day gets no motion, because motion there reads as lag. Every action gets visible acknowledgment: an immediate selected, open, or loading state counts; add press feedback only when the result leaves a gap. Hover alone never acknowledges activation.

These rules keep output off the generic default. When the committed direction truly needs to break one, break it on purpose and name the tradeoff in the handoff. The accessibility baseline and the CSS-pattern bans are never broken.

## Gotchas

| What happened | Rule |
| --- | --- |
| Relied on `…` truncation to fit a fixed-width slot | Guarantee fit: compact the format, cap to whole segments, or trim with no glyph. Metric and label footers never tail-truncate |
| One extra word wrapped a line and left a single orphan word | Check the container and forced breaks first; tighten repetition without losing meaning; never shrink type for a widow |
| Five text styles inside one small card | One style per role, hierarchy by order; more than three in a small block is the smell |
